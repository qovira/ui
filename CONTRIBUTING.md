# Contributing to @qovira/ui

Thanks for your interest in `@qovira/ui` — Qovira's Svelte 5 component library:
styled, accessible UI primitives and composites built on
[`@qovira/theme`](https://github.com/qovira/theme)'s design tokens. It's the
shared component layer for every Qovira surface, so changes here ripple across
the product. We're glad to have help keeping it sharp.

## Ground rules

- **Open an issue first.** Before sending a pull request — especially anything
  that adds a component, changes a prop, or alters a component's default
  behavior — open an issue so we can agree on the approach. A component library
  is a shared contract; a quick conversation up front saves a rejected PR later.
  Typo fixes and obviously correct documentation tweaks can skip straight to a PR.
- **Be kind.** This project follows the [Contributor Covenant](./CODE_OF_CONDUCT.md).
  By participating you're expected to uphold it; please report unacceptable
  behavior to the address listed there.
- **Licensing.** The project is [Apache-2.0](./LICENSE). Under section 5 of that
  license, any contribution you submit for inclusion is licensed under the same
  terms — opening a pull request is all the agreement we need. There's no CLA and
  no per-commit sign-off to remember.

## What belongs here

This package ships **components**, not visual values. Every color, font, radius,
shadow, and motion comes from `@qovira/theme`; `@qovira/ui` composes those tokens
into Svelte components and **defines no visual values of its own**. Keeping that
boundary tight is what lets the whole system share one source of truth.

**In scope** — contributions we welcome:

- New components and composites built **entirely** on the theme's semantic
  utilities (`bg-surface`, `text-text`, `focus-ring`, `rounded-md`,
  `text-button`, …).
- Bug fixes (a broken prop, a rendering edge case, a regression).
- Accessibility fixes — keyboard interaction, ARIA, focus management, anything
  that improves an axe result.
- Documentation: the README, this guide, Storybook stories, code comments.
- Tests, build, and tooling improvements.

**Out of scope** — please don't open a PR for these:

- **Hard-coded visual values.** A raw hex color, a magic `px` radius, a bespoke
  shadow — none of these belong here. A component that needs a token the theme
  doesn't expose is a signal to **extend `@qovira/theme`**, not to hard-code the
  value here. Open an issue against the theme (and link it here); see
  [Cross-repo changes](#cross-repo-changes-qoviratheme) below.
- **Application-specific UI.** A component only one Qovira surface needs lives in
  that surface, not in the shared library.
- **A second styling system.** No CSS-in-JS, no competing token set, no inline
  styles standing in for a missing token. The theme's utilities are the only
  styling vocabulary.

## Getting set up

You'll need **Node ≥ 24** and **pnpm** — pnpm is the only supported package
manager (npm and yarn are not used here). The pnpm version is pinned in
`package.json`; the easiest way to match it is [Corepack](https://nodejs.org/api/corepack.html),
which ships with Node:

```sh
corepack enable          # one-time; activates the pinned pnpm
pnpm install
```

Vitest runs components in a real browser (Browser Mode, Playwright provider), so
install the browser once:

```sh
pnpm exec playwright install --with-deps chromium
```

The scripts that cover the workflow:

```sh
pnpm dev          # vite dev — the SvelteKit playground app
pnpm storybook    # Storybook on :6006 — the component workbench
pnpm check        # svelte-kit sync && svelte-check (.svelte type + a11y)
pnpm typecheck    # svelte-kit sync && tsc --noEmit (.ts)
pnpm lint         # eslint + prettier --check
pnpm test         # vitest run --project unit --project storybook
pnpm package      # svelte-package + clean + publint (the publishable build)
```

Run `pnpm format` to apply Prettier. Before you open a PR, the full gate below
should pass — that's exactly what CI runs.

## How the codebase is organized

Everything ships from `src/lib`; `dist/` is generated by `svelte-package`, never
edited by hand. The library ships **uncompiled `.svelte` source** — the
consumer's own Vite/Tailwind compiles it.

| Path                        | What it is                                                                               |
| --------------------------- | ---------------------------------------------------------------------------------------- |
| `src/lib/index.ts`          | The **public barrel** — the single entry point. If it isn't exported here, it's private. |
| `src/lib/components/`       | The components (`*.svelte`), their variant tables (`*.ts`), and co-located stories.      |
| `src/lib/icons/`            | The `<Icon>` wrapper over `phosphor-svelte` and its exported types.                      |
| `src/lib/internal/`         | Internal helpers — e.g. `cn.ts`. **Not** exported from the barrel.                       |
| `src/routes/`               | The SvelteKit playground app (`pnpm dev`); not published.                                |
| `scripts/clean-package.mjs` | Strips stories/tests from `dist/` after `svelte-package`.                                |

## Authoring components

A few conventions are load-bearing — read them before adding a component:

- **Theme utilities only.** Author components in `@qovira/theme`'s semantic
  utilities (`bg-surface`, `text-text`, `text-button`, `rounded-md`, …). No raw
  colors or off-grid values. (See [What belongs here](#what-belongs-here).)
- **`focus-ring` on every interactive element**, and it must be the **last**
  class in the `cn()` call so a consumer's `class` can't merge it away. This is
  the most-enforced a11y rule — never drop it.
- **Merge the consumer `class` with `cn()`** (`src/lib/internal/cn.ts`, clsx +
  tailwind-merge) so consumer classes win conflicts. `cn()` is internal — don't
  export it.
- **Public surface is the barrel** (`src/lib/index.ts`). Internal imports are
  **relative with explicit `.js`/`.svelte` extensions** (a `svelte-package`
  requirement) — never `$lib`.
- **Export consumer-facing types from a plain `.ts`** (e.g. a `*-variants.ts` or
  `icons/types.ts`), not re-exported from a `.svelte` module — the ambient
  `*.svelte` type only carries the default export, so `svelte-check` can't see
  named type re-exports from `.svelte`.
- **Stories are Svelte CSF** (`*.stories.svelte` with `defineMeta`), co-located
  with the component, `tags: ['autodocs']`, and a11y `test: 'error'`. For a story
  that renders custom markup or multiple instances, use
  `{#snippet template()}…{/snippet}` — a bare `<Story>` child renders as the meta
  component's children and double-wraps compositions. Arg-only stories
  (`<Story args={…} />`) don't need it.

## Testing and accessibility

Tests run with Vitest (`pnpm test`) across two projects: **`unit`** (logic) and
**`storybook`** (every story rendered and interaction-/a11y-tested in a real
browser via Playwright). Storybook's a11y addon runs axe with `test: 'error'`, so
an accessibility violation **fails the build** — accessibility is enforced, not
aspirational.

Keeping CI green is the floor, not the ceiling. Adding to the library means
adding to its tests:

- **A new component** ships with a story (which gives you render + a11y coverage)
  and unit tests for any non-trivial logic (variants, state, keyboard handling).
- **A bug fix** includes a regression test that fails before your change and
  passes after.
- If an axe rule genuinely can't be satisfied from the current tokens, that's a
  theme gap — not a reason to relax the rule silently. Flag it in your issue/PR;
  see the next section.

## Cross-repo changes (`@qovira/theme`)

`@qovira/ui` consumes `@qovira/theme` as a **peer dependency** from npm. If your
change needs a token or value the theme doesn't expose, **don't hard-code it
here** — the fix belongs upstream:

1. Open an issue (here and/or on `@qovira/theme`) describing the missing token.
2. The token lands and is released in `@qovira/theme` first.
3. `@qovira/ui` bumps its dependency and consumes the new token.

A contributor PR can't span both repos, so note the dependency in your issue and
a maintainer will help sequence the theme release. (The README's "Known issues"
and `CLAUDE.md` track any live examples of this debt.)

## Opening a pull request

Once there's an issue and your change is ready:

1. **Branch** off `main` and make your change there.
2. **Keep it scoped.** One logical change per PR. A focused diff is reviewed
   faster than a sweeping one.
3. **Run the full gate locally** — `pnpm check && pnpm typecheck && pnpm lint &&
pnpm test && pnpm package` — before you push. CI runs exactly these, and they
   must be green to merge.
4. **Add a changeset** for any user-facing change (see [Changesets](#changesets)).
5. **Write a clear PR description.** Say what changed and why, and link the issue
   it resolves.

### Changesets

User-facing changes are versioned with [Changesets](https://github.com/changesets/changesets).
If your change affects consumers, run `pnpm changeset` and commit the generated
file — it prompts for the bump level and a summary:

- **major** — a prop removed or renamed, a changed default behavior, or a raised
  `@qovira/theme` peer range.
- **minor** — a new component, or an additive (optional) prop.
- **patch** — a backward-compatible bug fix, no API change.

A changeset is the most useful thing you can add, but it's not a blocker — if
you're unsure of the level or forget, a maintainer will add one on merge. See
`.changeset/README.md`.

### Commits

We use [Conventional Commits](https://www.conventionalcommits.org/) on `main`,
but **you don't have to**. PRs are squash-merged, and a maintainer writes the
final Conventional Commit message on merge. So:

- Give the **PR** a clear, descriptive title and a useful description — that's
  what we work from.
- Your individual commits can be whatever helps you; they won't survive the
  squash.

### Review

A maintainer will review for correctness, scope, accessibility (does it pass axe,
and is `focus-ring` intact?), and fit with the theme-utilities-only boundary.
Expect a conversation — it's how we keep the library coherent. Once it's approved
and green, we squash and merge.

## Releases

Releasing is **maintainers only** — there's nothing for a contributor to do here
beyond landing a changeset, but it's documented so the process isn't a mystery.
Versioning and the changelog are driven by Changesets: `pnpm version-packages`
(`changeset version`) consumes the pending changesets on `main`, bumps
`package.json`, and updates `CHANGELOG.md`. Pushing the matching `v*` tag triggers
the release workflow, which runs the full gate on Blacksmith and then publishes
`@qovira/ui` to npm from a GitHub-hosted job via OIDC **Trusted Publishing** with
a signed provenance attestation (no `NPM_TOKEN`). The published tarball is
`dist/` only.
